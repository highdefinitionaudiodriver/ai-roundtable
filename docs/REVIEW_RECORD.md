## 1. 重大リスク（HIGH） — 公開前に必ず対処を推奨

### H-1. 「複数AIの議論」というUIだが実体は単一モデルのロールプレイ
- 該当: `server.py:88-106` の `run_roundtable`、`call_provider` の分岐は **1リクエスト内で provider が固定**。reviewer / skeptic / expander / synthesizer はすべて同じ provider・同じモデルで生成される。
- リスク: ユーザーは「他社AIによる相互チェック」を期待する文脈で利用するが、実際は **同一モデルが役割演技しているだけ**。同一モデル特有のバイアス（学習データ偏り・特定ドメインの過信）は議論を重ねても消えず、むしろ **synthesizer が誤りを「合意済み結論」として固める** 危険がある（エコーチェンバー）。
- 人生影響度: 高（医療・法務・金融などで「3つのAIが同意した」という誤認が最終判断に直結しうる）。
- 推奨対応:
  - 役割ごとに provider を切り替えられるオプションを追加（既存の `provider` セレクタを役割別配列に拡張）。
  - UI に「同じAIが複数の視点を演じています／別社AIで再検証するには共有プロンプトを使ってください」と**常時表示**。
  - synthesizer の出力には必ず「これは単一モデルの自己整合の結果である」旨のフッターを付ける（システムプロンプトで強制）。

### H-2. CORS が全オリジン許可 + POST に CSRF 防御なし
- 該当: `server.py:38-46` で `Access-Control-Allow-Origin: *` を全レスポンスに付与。`/api/roundtable` `/api/roundtable-step` は POST だが Origin/Referer 検査・トークン検査なし。
- リスク: ローカルで `python server.py` を起動している間、**ユーザーが訪問した任意のウェブサイト**が JavaScript から `http://127.0.0.1:8787/api/roundtable` を叩ける。これにより、
  1. ユーザーの API キー（OpenAI/Anthropic/Gemini）を**第三者サイトが任意のプロンプトで消費**できる（金銭被害）。
  2. 攻撃者が選んだ文章をプロバイダに送信し、応答を読み取れる（プライバシー漏洩・ログ汚染）。
  3. `auto` モード相当のリクエストを連射してレートリミット枯渇・課金爆発。
- 人生影響度: 中〜高（API キーの請求が膨らむ／業務用キーなら情報漏洩経路化）。
- 推奨対応:
  - `Access-Control-Allow-Origin` を `http://127.0.0.1:8787` 限定に。`*` は完全に外す。
  - POST は `Origin` ヘッダが許可ホストと一致するかをサーバ側で必須チェック。
  - さらに、起動時に生成したランダムトークンを cookie もしくは meta タグ経由で配り、POST に `X-CSRF` ヘッダ必須化（最も堅い）。

### H-3. 安全ガードがクライアント側のみ（サーバが素通し）
- 該当: `public/app.js:138-203` の `blockedRules` / `highRiskRules` / `ensureSafeToProceed`。`server.py` 側には **同等のチェックが一切ない**。
- リスク: ブラウザ UI を経由しない呼び出し（H-2 の CORS 経路、curl、ブックマークレット改変、別ページからの fetch、PWA キャッシュ汚染）では **ブロック判定が完全に無効**。「自傷・違法・武器・詐欺の支援はしない」という公開宣言と乖離する。
- 人生影響度: 高（自傷誘発・違法行為支援が「ブロックされる前提」で UI に書かれているのに、実際は迂回可能）。
- 推奨対応:
  - `server.py` の `do_POST` 入口で同じルールを Python 実装し、`blocked` ヒット時は 4xx で拒否し、ヒット内容のログ（個人情報は伏字化）を残す。
  - クライアント側ルールは UX 向上のための先回り表示、サーバ側ルールが**正本**、という二層構造に。

### H-4. 自動議論ループに上限がない
- 該当: `public/app.js:382-422`。`while (state.autoRunning)` で停止ボタンが押されるまで無限に呼び続ける。900ms のスリープのみ。
- リスク:
  - ユーザーが画面を閉じ忘れる・スマホをポケットに入れたままなどで**深夜にAPIが回り続け請求が膨張**。
  - 高リスクトピック（医療など）で自己強化的に**過信を蓄積した結論**を量産しうる。
  - トランスクリプトが肥大し、毎リクエストの prompt が線形に伸びてコスト二次関数的増大。
- 人生影響度: 中（金銭被害 + 誤助言の固定化）。
- 推奨対応:
  - **必ず**最大ターン数（例: 8–12）、最大トークン累計、最大経過時間のいずれかをハードリミットに。UI から変更可だが上限あり。
  - `transcript` をそのまま積むのではなく、N ターンごとに要約して縮める。
  - 高リスクトピックは自動議論そのものを禁止（H-7 と連動）。

### H-5. ハイリスク確認ダイアログが「チェック1個 + 続行」で形骸化しやすい
- 該当: `public/app.js:205-244`、`public/index.html:105-119`。
- リスク: 文言は妥当だが、毎回同じダイアログ・1クリックの摩擦しかなく、**儀式化**する。特に医療・自殺関連の境界（うつ / pregnan / 自傷未満の表現）で「とりあえずチェックして続行」される。
- 人生影響度: 高（うつ・妊娠・服薬・契約・解雇など、まさに人生に直結する領域）。
- 推奨対応:
  - 高リスクカテゴリ別に**異なる注意文**（医療なら「医療機関 / #いのちの電話 0120-783-556」等の具体的窓口）。
  - 自殺・自傷の弱いシグナル（"消えたい" "つらい" 等）を `blockedRules` ではなく**高リスク + 相談窓口の必須提示**に格上げ。現状の `blockedRules` の self-harm パターンは「死にたい」等の強い表現のみで、その手前の SOS を捉えていない。
  - 専門家相談チェックを「同意」ではなく**情報提示**（窓口リンク表示）に置き換える。同意UIは責任転嫁になりやすい。

## 2. 中リスク（MEDIUM）

### M-1. 正規表現ガードは脆く、誤検知・取りこぼし両方が起きる
- 該当: `public/app.js:138-151`。
- 例:
  - 「**メンタル**ヘルス**研修**の相談」 → 医療フラグ。誤検知で UI 摩擦。
  - 「unalive myself」「end my life」「自死したい」の一部表現や中国語・韓国語・スペイン語・フランス語の自傷表現を捕捉できない（多言語対応をうたっているのに英・日のみ）。
  - 「投薬計画」「自殺ほう助」「銃刀法」など漢字の組み合わせ・ローマ字化・伏字（"じ●つ"）に弱い。
- 推奨対応: 多言語パターンの追加、または provider 側のモデレーション API（OpenAI Moderations 等）を**サーバ側で**呼んで判定。少なくとも対応宣言言語（ja/en/zh/ko/es/fr）に対するパターンは網羅すべき。

### M-2. システムプロンプトに「自傷・違法・専門助言禁止」の明示が弱い
- 該当: `server.py:18-22`。「high stakes ならカヴェアットを付けろ」とあるのみ。`ROLE_PROMPTS` の skeptic は "Look for hidden assumptions" と書かれており、**自殺・自傷文脈で「リスク」を煽る方向に展開しうる**。
- 推奨対応: システムプロンプトに「自傷・違法行為・武器・他者加害については議論ではなく相談窓口の提示で返す」「医療・法務・金融については**個別具体的な助言を出さず**論点整理に留める」を明示。役割プロンプトにも同制約を追記。

### M-3. プライバシー — 入力がそのまま3社に転送されることの説明不足
- リスクダイアログ (`riskMessage`) は「最終判断に使うな」とだけ書き、**入力テキストが OpenAI/Anthropic/Google に送信されること**を伝えていない。SAFETY_NOTES には記載があるが、**実行直前の同意プロンプトに含めるべき**。
- 「個人情報・パスワード」検出時もダイアログを出すだけで実行は止めない（`highRiskRules` 扱い）。実行直前に「送信先: OpenAI」と明示し、個人情報パターン検出時は**送信を既定でブロック**に。

### M-4. URL クエリ import の信頼境界が曖昧
- 該当: `public/app.js:335-346`。`quote`, `source`, `title` を `.value` に入れている（textContent 経由ではないが、`textarea.value` なので XSS は無し）。問題は**社会的攻撃**:
  - 攻撃者が「これを AI Roundtable で確認してください」と細工した URL（怪しい質問が prefill 済み）を送る → ユーザーが何気なく実行 → API キー消費・誤った安心の獲得。
- 推奨対応: URL から prefill した場合、**赤バナーで「外部URLから取り込まれた内容です」と明示**し、自動実行・自動議論ボタンを一段ガード。

### M-5. ブックマークレットの設計
- 該当: `public/app.js:273-276`。`location.href` と選択テキスト（最大4000文字）を URL クエリで `open()`。
- リスク: ブラウザ履歴・親プロセスのプロセスリスト・社内プロキシログに**機密テキストが残存**しうる。
- 推奨対応: ブックマークレットを `postMessage` ベースに、または `sessionStorage` 経由に。少なくとも README に「履歴に残ります」と明記。

### M-6. PWA Service Worker のキャッシュに古い `app.js` が残る
- 該当: `public/sw.js`。`?v=5` でキャッシュ世代分離はしているが、ユーザー側で safety ルール更新後に**古いキャッシュ版を使い続ける**可能性。安全ルール更新がリリースされても反映が遅れる。
- 推奨対応: `app.js` と `sw.js` は network-first にし、安全更新を即時配布できるように。

### M-7. プロバイダ呼び出しのトークン上限
- 該当: `call_anthropic` は `max_tokens: 1000`、`call_openai`/`call_gemini` は未指定（プロバイダ既定）。Gemini は安全設定（`safetySettings`）も未指定で既定動作。
- 推奨対応: 3社とも明示的に `max_tokens` を設定し、Gemini は `safetySettings` を明示（例: HARM_CATEGORY_SELF_HARM を BLOCK_LOW_AND_ABOVE）。

## 3. 低リスク（LOW） / 設計上の指摘

- **L-1**: `server.py:71-72` の `except Exception as exc: write_json({"error": str(exc)}, status=500)` は内部例外メッセージをそのまま返す。プロバイダのエラー本文（API キー断片を含む可能性）が漏れうるので、サーバログには詳細・クライアントには汎用文に分離を推奨。
- **L-2**: `i18n` の zh/ko/es/fr が **en の浅いコピー**で、`riskMessage` 等の重要文言が英語表示のまま。多言語ユーザーに対して安全文言が母語で伝わらない。
- **L-3**: `aiTargets` で 6 社の外部 AI ページを開くリンクがあるが、共有プロンプトのクリップボードコピーが**ユーザーの認識なしに発生**（リンククリック時に自動コピー）。挙動の明示があると良い。
- **L-4**: `OPENAI_MODEL` 既定が `gpt-4o-mini`、`ANTHROPIC_MODEL` が `claude-3-5-haiku-latest`、Gemini が `gemini-1.5-flash` — 安価モデル既定は妥当だが、**高リスク領域でこそ安価モデルで判定するのは危うい**。せめてリスクダイアログを通過したケースは上位モデルにフォールバックする選択肢を。
- **L-5**: ポートが固定で `0.0.0.0` ではなく `127.0.0.1` 限定 → 良い（LAN 漏出なし）。維持。
- **L-6**: `directory=PUBLIC` で SimpleHTTPRequestHandler に渡しており、静的配信のディレクトリトラバーサルは標準ライブラリ側で防御。問題なし。
- **L-7**: ライセンスは MIT で OK。ただし README に「No warranty — 医療・法務・金融判断に使わないこと」を MIT 標準免責に加えて**ユーザー向け平文**で目立たせると良い。

## 4. 良い点（維持したい設計）

- API キーをブラウザに露出せず、ローカル Python サーバ経由で隠蔽している（`SAFETY_NOTES.md` の通り運用されている）。
- `127.0.0.1` バインドで LAN への意図せぬ公開を回避。
- ローカル keyword ガード + ハイリスク確認ダイアログという**二段ガード思想**自体は健全。
- システムプロンプト末尾の「Do not claim to have consulted other AIs」は誠実な制約で、ロールプレイ性の正直な開示につながる。
- ドキュメント類（SAFETY_NOTES / PUBLICATION_CHECKLIST）が整備されており、公開リスクを設計者が認識している痕跡がある。
- 自動議論に「停止」ボタンがあり、`setBusy` で UI が同時実行を抑制している。

## 6. 公開可否についての所見

「個人利用・自分の責任で他AIの回答をセカンドオピニオン的に眺める道具」としての公開は、**P0 4 項目を片付ければ許容範囲**だと考えます。一方で、

- 「AI同士で議論させて結論を得るツール」と読める広報文（X 投稿ドラフト含む）で公開すると、ユーザーは H-1 の誤認を前提に行動します。
- 「自殺・うつ・契約・解雇・服薬・移民・税」などのキーワードは現実に検索されます。このアプリの UX は「他AIに相談すれば客観性が増す」という錯覚を強める方向に作用するため、**広報文と UI 双方で「単一モデルの自己対話である」「最終判断には使わない」「具体的な相談窓口」を明示**してください。

人の人生にかかわる用途では、**ツール自体の堅牢さ以上に「期待値の正直な開示」が安全装置になります**。技術修正と並行して、コピーライティング（README / 起動画面 / ダイアログ文）を見直すことを強く推奨します。
